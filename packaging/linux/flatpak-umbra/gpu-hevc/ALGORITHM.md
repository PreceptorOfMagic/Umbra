# Parallel CABAC arithmetic component

**ESTABLISHED — implementation scope:** `cabac_parallel.cl` consumes the same
ordered bin operations and initialized context states as the serial reference.
It produces one CABAC substream, including trailing byte alignment, before NAL
emulation-prevention insertion. It creates no additional slices, tiles, WPP
entry points, picture references or frame-to-frame dependency. The current host
driver is a development test harness, not an Apollo encoder.

**ESTABLISHED — supported state domain:** the parallel implementation uses packed
context states 0–125 and normalized arithmetic ranges 256–511 (510 initially).
Packed states 126/127 are rejected when used. This follows the state range
generated by pinned x265's [`sbacInit`, entropy.cpp:1693](https://bitbucket.org/multicoreware/x265_git/src/b81f650e21e8aacbe6a9ad04ce14aefc05b932c0/source/encoder/entropy.cpp#lines-1693)
and its transition table. It is not a general replacement for hypothetical
callers supplying arbitrary internal arithmetic-coder states. Contexts must not
reset within the supplied single slice.

## Context states and arithmetic ranges

**ESTABLISHED — source mechanism:** context updates depend on earlier bins using
the same context. The GPU stably groups regular bins by context, preserving order
within each group. Context boundaries reset to the supplied initial model. It
constructs the transition function of each 32-bin block for all 128 possible
incoming packed states. Functions compose associatively: applying a left block
and then a right block is `right(left(state))`.

The GPU scans these functions and resolves each block's actual incoming state.
It then writes the actual pre-bin model back to each operation's original
position. The trace's expected state is consulted **only** in the validation
trial. The measured trials compute their own models with this GPU pipeline.

Once those models are available, the GPU computes analogous transition functions
for 32-operation blocks over the 256 incoming normalized ranges. Scanning those
functions determines each block's actual incoming range without traversing the
entire slice in one thread. Operations are evaluated in their original order for
this range computation; the earlier context grouping does not reorder the coded
syntax.

Local groups scan 32 transition functions and publish a smaller tile summary.
Only summaries pass through the global composition scan. Histogram prefixes,
bit-count sums and carry propagation use similar bounded local scans to avoid
many whole-array passes. These computational tiles are unrelated to HEVC tiles.

## Low value and carry assembly

**ESTABLISHED — implemented derivation:** each operation can be represented as

`low_after = (low_before << shift) + additive`.

With the correct incoming range and model known, both `shift` and `additive` are
independent of the previous `low`. Regular MPS bins add zero. LPS bins add the
selected lower interval shifted by their renormalization count. Bypass bins add
`range * bin_values`; the shift is the number of bypass bits. Termination uses
the corresponding x265 interval update.

Let `T_i` be the accumulated shift through operation `i`, and `T` its final value.
The unbounded final low value is the sum of
`additive_i << (T - T_i)`. Rather than maintain a huge integer, GPU work items
accumulate each additive into its affected base-256 digits. Arithmetic uses
integer operations. Bypass runs up to 32 bits use 64-bit additive storage.

For each accumulated digit `D_i`, let `G_i = D_i >> 8`. Its remaining carry is a
Boolean `e_i`, with `e_-1 = G_-1 = 0`:

`e_i = ((D_i & 255) + G_(i-1) >= 256) OR`
`      (((D_i & 255) + G_(i-1) == 255) AND e_(i-1))`.

This generate/propagate recurrence is another associative scan. The normalized
digit is `(D_i + G_(i-1) + e_(i-1)) & 255`. Packing drops the low eight bits of
the final low value, emits `T + 1` coding bits, and appends x265's alignment one
and zero padding. Consequently, output carry propagation no longer serializes
all bins or bytes.

**ESTABLISHED — validation extent:** the independent pinned x265 oracle, native
8-/10-bit pane fixtures and generated edge-case vectors establish bit exactness
for the tested inputs on the tested drivers. They are not formal verification of
all possible HEVC streams. Output-capacity checks and explicit rejection tests
are additional checks, not a production security qualification.

## What the timings omit

**ESTABLISHED — limits:** the benchmark starts with complete bin operations
already resident on the GPU. GPU grouping, transitions, scans, carry assembly,
scratch clearing and final packing are timed. Capture, mode search, transforms,
reconstruction, syntax binarization, operation upload, buffer allocation,
networking and presentation are outside the device interval. The separate host
interval includes submission and payload readback. The kernel runs with scratch
storage proportional to operation count; the test does not measure game
contention or overlapping encoder frames. The harness uses reference-sized
output storage with 64 bytes of spare capacity, not a production allocation policy.

**HYPOTHESIS — integration:** this can remove the serial arithmetic bottleneck
from a future GPU x265-derived encoder. It does not prove that the remaining
encoder can deliver bins quickly enough, that whole-slice coordination preserves
the required frame age, or that GPU/memory contention preserves game performance.
